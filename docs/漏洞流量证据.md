# 취약점의 다중 트래픽 증거

취약점 상세 화면의 「연결 트래픽」은 여러 페이지에 걸친 다중 선택, 용도와 설명, 정렬 및 연결 해제를 지원합니다. 트래픽 페이지에서도 여러 기록을 선택해 기존 취약점 하나에 연결할 수 있습니다. 작업에서 상속한 취약점 증거는 읽기 전용이며 수정하려면 원본 작업으로 이동해야 합니다.

시스템 설정의 「에이전트 트래픽 자동 연결」은 기본적으로 꺼져 있으며 `/api/settings`의 `agent_traffic_binding`으로 조회·수정합니다. 활성화하면 요청/응답 확인, 도구 호출 및 프롬프트에 따른 토큰 사용량이 증가하며 다음 에이전트 턴부터 새 설정을 사용합니다. 비활성화하면 자동 연결 매개변수와 추가 연결 도구를 숨기고 자동 연결 지침을 삽입하지 않으며, 이미 실행 중인 세션이 새로 제출하는 자동 연결도 거부합니다. 수동 연결, 트래픽 캡처, 저장된 증거의 읽기·내보내기는 영향을 받지 않습니다.

활성화한 경우 기본 흐름은 「발견 등록 → 보고서 에이전트 자동 실행 → 트래픽 확인 및 연결 → 최신 증거 버전으로 보고서 작성」입니다. 보고자는 `evidence`에 검증 명령, 핵심 출력, 이미 확보한 실제 트래픽 ID와 용도를 보존합니다. 보고서 에이전트는 취약점 상세 정보와 실행 기록을 종합하여 `traffic_search` / `traffic_get`으로 확인한 뒤 `bind_finding_traffic`을 호출하고 최신 `version`을 읽어 보고서를 저장합니다. 비활성화한 경우 보고서 에이전트에 원본 트래픽 검색·읽기 도구를 추가 제공하지 않고 자동 연결도 수행하지 않지만, 수동으로 연결한 스냅샷을 읽어 보고서를 생성할 수 있습니다.

기존 호출자와의 호환성을 위해 `report_finding`의 `traffic_refs` / `evidence_hint_id`로 명시적인 즉시 연결도 가능합니다. 연결은 선택 사항입니다. TCP 등 비 HTTP 취약점, 미수집 상황 또는 정확한 기록을 찾지 못한 경우 인용을 생략해도 정상 등록·보고서 작성이 가능합니다. 명령 출력·로그 등 검증 가능한 다른 증거를 보존하고 미연결 이유를 설명하는 것을 권장하며 새 필수 필드는 추가하지 않습니다. 제출하는 ID는 모두 유효하고 본문이 완전해야 합니다. 하나라도 실패하면 이번 연결 동작을 롤백하며, 등록과 함께 명시적으로 연결하다 실패하면 전체 등록을 롤백합니다. 같은 스냅샷을 반복 추가해도 연결을 늘리거나 설명을 덮어쓰지 않습니다.

## 에이전트 ID와 보고서 버전

`report_finding`에 추가된 선택 매개변수에서 배열 순서는 초기 증거 순서입니다.

```json
{
  "traffic_refs": [
    {"traffic_id": "실제 트래픽 ID", "role": "baseline", "note": "정상 계정 요청"},
    {"traffic_id": "다른 실제 트래픽 ID", "role": "proof", "note": "재현 요청"}
  ]
}
```

용도는 `baseline`(정상 대조), `proof`(취약점 입증), `verification`(추가 검증), `supporting`(보조 증거, 기본값)입니다. 먼저 `traffic_search` / `traffic_get`으로 실제 기록을 확인하세요. 도메인과 시각은 후보 선별에만 사용하며 작업 귀속을 추정하지 않습니다.

프롬프트는 [CyberStrikeAI 취약점 보고 도구 지침](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go)을 참고하되 이 프로젝트의 선택적 연결 규칙을 적용하며, 패킷이 없는 이유를 필수로 검사하지 않습니다. ID를 추측하거나 패킷을 채우기 위해 같은 탐지를 반복하면 안 됩니다.

반환 첫 줄은 여전히 `finding recorded: <탐색 노드 ID>`이며, 이어지는 JSON에서 독립 취약점 기록 `finding_id`, 탐색 노드 `finding_node_id` 및 연결 요약을 제공합니다.

- `get_finding_traffic(finding_id)`는 **독립 취약점 기록 ID**를 사용하고 정렬된 목록과 `version`을 반환합니다. `binding_id`, `side=request|response`, `offset`, `length`로 나누어 읽을 수 있으며 한 번에 최대 8192바이트입니다.
- `update_finding_report`의 `finding_id`는 **계속 탐색 노드 ID를 사용합니다**. 새 `evidence_version`에는 실제 읽은 버전을 넣습니다. 생성 중 증거가 바뀌면 이전 버전 쓰기를 거부하므로 다시 읽고 생성해야 합니다.
- 이전 보고서 호출에서 버전을 전달하지 않으면 기존 트래픽 증거를 반영했다고 주장하지 않습니다. 연결·설명·용도·정렬이 바뀌면 기존 보고서는 갱신 필요로 표시됩니다.

자동 연결을 켜면 `add_hint` / `add_task_hint`의 단일 힌트 또는 일괄 `hints` 요소마다 `traffic_refs`를 저장할 수 있습니다. Planner가 대신 등록할 때 `evidence_hint_id`로 이 작업의 해당 힌트에 있는 인용을 명시적으로 선택할 수 있으나 상속한 힌트는 참조할 수 없습니다. 도메인·시각·방문 기록으로 연결을 추측하지 않습니다. 제출에 실패하면 일부 취약점을 생성하거나 보고서를 조기 실행하지 않습니다.

이미 등록한 취약점에 연결이 빠졌다면 `bind_finding_traffic(finding_id, traffic_refs)`로 추가 연결하며 중복 등록할 필요가 없습니다. `list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail`은 명시적인 `finding_id`와 `finding_node_id`를 반환하고, 기존 `id`는 탐색 노드 의미를 유지합니다.

시작 시 이전 도구 schema에는 선택 속성만 추가하고 원래의 기본 트래픽 도구 연결을 보고서 에이전트까지 확장합니다. 추가 연결 도구는 기본적으로 보고서 에이전트에 배정합니다. 사용자 지정 연결 목록, 프롬프트, 설명 및 활성화 상태는 보존합니다. 최종 도구 조립 후 지침을 일괄 삽입하며, 보고 역할은 기존 증거 전달을 담당하고 보고서 에이전트는 확인·연결·작성을 담당합니다. 플랫폼 대화에 작업 컨텍스트가 없으면 직접 등록하지 말고 구조화된 힌트로 작업 에이전트에 전달해야 합니다. 작업 완료 판정 전에 확보한 증거를 먼저 전달하며, 패킷이 없다고 강제로 기다리지 않습니다. 실패한 `report_finding`은 보고서 에이전트를 실행하지 않습니다.

## API

기본 경로는 `/api/exploration/findings/{finding_id}/traffic`이며 독립 취약점 ID를 사용합니다. 기존 인증을 유지하고 `context_task`로 작업 가시성과 상속 읽기 전용을 검사합니다.

| 메서드 / 상대 경로 | 요청 / 반환 |
| --- | --- |
| `GET` | 정렬된 요약, 증거 버전, 보고서에 적용한 버전 |
| `POST` | `{"traffic_refs":[...]}` 묶음 전체 추가 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"설명"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`, 반드시 전체 목록 |
| `GET /{binding_id}` | 스냅샷 메타데이터와 길이가 제한된 본문 미리 보기 |
| `GET /{binding_id}/body` | `side`, `offset`, `length`; `download=1`이면 원본 전체 바이트 다운로드 |

버전/정렬 집합 충돌이나 보관 중 쓰기는 `409`, 상속한 증거에 대한 쓰기는 `403`, 존재하지 않거나 해당 취약점 소속이 아닌 연결은 `404`입니다. 트래픽·첨부 파일 읽기 또는 검증 실패는 명시적인 오류를 반환합니다.

## 저장과 마이그레이션

시작 시 PostgreSQL에 멱등 마이그레이션을 적용하여 `traffic_evidence_snapshots`, `finding_traffic_bindings`, `findings.evidence_version` / `report_evidence_version`(기본 0)을 추가합니다. 과거 텍스트를 바탕으로 연결을 추측하지 않습니다.

스냅샷은 원래 트래픽 ID, 수집 시각, URL, 메서드, 상태, 요청/응답 헤더, 본문 길이와 SHA-256을 저장합니다. 본문은 해시별로 `<data>/evidence/blobs/<앞 두 자리>/<hash>.bin`에 저장하며 정리 가능한 `data/traffic`과 독립적입니다. 여러 취약점이 스냅샷/본문을 공유할 수 있습니다. 스냅샷 내용 갱신 API는 제공하지 않으며 검증 불일치 시 읽기·내보내기가 실패합니다.

원본 트래픽 쓰기 잠금 아래에서 큰 본문 blob과 이전 디렉터리 기록을 포함한 전체 본문을 읽습니다. 먼저 파일을 영구 저장·검증한 후 단일 PostgreSQL 트랜잭션으로 탐색 노드, 의도 관계, 취약점, 스냅샷 및 연결을 기록하며 커밋 후에만 계획자에게 알립니다. 실패하면 참조 없는 파일이 남을 수 있지만 일부 업무 기록만 생성되지는 않습니다.

PostgreSQL advisory lock `7337741004`가 증거 파일과 SQL 참조를 조정하고, 작업 행 잠금이 보관 대기열 등록 후 증거 수정을 차단합니다. 복원은 본문 설치부터 메타데이터 커밋까지 증거 잠금을 유지합니다. 취약점 삭제 시 연결을 연쇄 삭제합니다.

정리기는 매시간 실행되며 참조가 없고 진행 중인 동작에 속하지 않는 내용만 최소 24시간 후 회수합니다. 일반 트래픽 정리는 증거 디렉터리에 영향을 주지 않습니다. 활성 데이터를 백업할 때 PostgreSQL과 `data/evidence`를 함께 백업하세요.

## 내보내기와 보관

Markdown에는 정렬된 증거 목록과 버전, JSON에는 메타데이터, CSV에는 건수와 연결 ID를 포함합니다. `md-zip`은 취약점 Markdown을 보존하고 다음 파일을 제공합니다.

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown은 상대 링크로 메시지를 참조합니다. 다운로드 전송 전에 첨부 파일 복사, 해시 검증, 압축, 디스크 동기화 및 모든 ZIP 항목의 CRC 읽기 검증을 완료합니다. 누락·손상이 있으면 전체 다운로드가 실패하며 첨부 파일은 바이너리 원본 바이트를 보존합니다.

보관 v3는 취약점 연결 관계에 따라 스냅샷과 본문을 수집하며 원본 트래픽이나 도메인에 의존하지 않습니다. 패키지를 검증한 뒤 활성 데이터를 정리하고 공유 증거는 보존합니다. 복원 시 본문을 검증·설치한 뒤 트랜잭션으로 메타데이터·연결을 복원하며 실패 후 재시도를 지원합니다. v1/v2도 복원 가능하고 없는 새 필드는 명시적으로 0으로 채웁니다.

## 검증과 한계

각 테스트 패키지에 독립적으로 새 PostgreSQL 테스트 DB를 만들고 `ARTEX_PG_DSN`으로 지정하여 남은 작업·모델 테스트 데이터가 실행되는 것을 피하세요. 관련 패키지 전체 테스트를 실행하고 설정 누락으로 건너뛴 항목이 없는지 확인합니다.

```sh
# 각 패키지 실행 전 ARTEX_PG_DSN을 해당 독립 테스트 DB로 설정하세요. 명시한 설정의 연결 실패는 반드시 오류로 처리합니다.
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

프런트엔드 검증에는 `npx tsc --noEmit`, 영향받는 파일의 Biome 검사, Webpack 빌드 및 `NEXT_EXPORT=1` 정적 내보내기를 포함합니다. 실행 중인 개발 서비스의 캐시를 덮어쓰지 않도록 독립 캐시 디렉터리를 사용합니다.

로컬 종단 간 검증은 별도 포트, 통제된 HTTP / 도메인 HTTPS 대상과 임시 데이터 디렉터리를 사용합니다. 두 연결 진입점, 페이지 간 선택, 정렬·설명, 오류 표시, 상속 읽기 전용, 다운로드 및 원본 트래픽 삭제 후 내보내기·보관·활성 본문 회수·복원·해시 검증을 포함합니다.

첫 버전은 전역 증거 조정 잠금을 사용하므로 대량 연결·내보내기 또는 느린 첨부 파일 다운로드 중 다른 증거 작업이 기다릴 수 있습니다. 기록이나 완전한 본문이 없으면 증거를 만들어내면 안 됩니다. 이 기능은 캡처 설정을 바꾸지 않으며 HTTPS로 IP에 직접 접근할 때의 인증서 문제도 처리하지 않습니다.
